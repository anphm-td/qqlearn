# Workflow: Thiết kế hệ thống RAG tài liệu TOEIC (có chống trùng lặp)

## Bối cảnh
Workspace `E:\PROJECT\rag_toeic` đang trống hoàn toàn (chỉ có `.zcodeignore`) → workflow thiết kế từ đầu, không phải tích hợp code sẵn có. Yêu cầu đã chốt: **tài liệu thiết kế chi tiết (không viết code), stack Python, hạ tầng local-first** (ChromaDB/FAISS + embedding mã nguồn mở, LLM qua API hoặc Ollama).

## Sản phẩm cuối
File `docs/thiet-ke-rag-toeic.md` — tài liệu thiết kế bằng tiếng Việt (thuật ngữ kỹ thuật giữ tiếng Anh), xuất bản làm artifact chính (`primary: true`). Return theo shape `WorkflowReport` (conclusion / findings / verified / notCovered).

## Topology subagent (9 agents)
1. **phan-tich-tai-lieu-toeic** — phân tích đặc thù tài liệu TOEIC (ETS format, Part 1–7, đề thi/sách/transcript/từ vựng) → trả về typed `Constraints`: các loại tài liệu, đơn vị cấu trúc (part/passage/question), **rủi ro trùng lặp đặc thù** (cùng đề tái bản nhiều sách, giải thích lặp lại...), ràng buộc local-first/Python/Windows. Kết quả này là đầu vào chung cho toàn bộ designer.
2. **5 designer song song** (mỗi người một `SectionDraft {title, markdown, decisions[]}`, chạy `Promise.all`):
   - `thiet-ke-nhap-tai-lieu` — ingestion: parse PDF/DOCX/EPUB, metadata model (nguồn, số đề, part, skill), pipeline nạp tài liệu.
   - `thiet-ke-chia-chunk` — chunking theo cấu trúc TOEIC (part/passage/câu hỏi), kích thước, overlap, parent-child retrieval.
   - `thiet-ke-chong-trung-lap` — **yêu cầu trọng tâm của user, có designer riêng**: dedup 3 lớp — tài liệu (hash chính xác + MinHash/LSH near-dup), chunk (SimHash + cosine ngưỡng embedding), và chính sách ingestion (giữ bản canonical, hợp nhất metadata, provenance) + cách đo tỷ lệ trùng trước/sau.
   - `thiet-ke-truy-xuat` — retrieval: ChromaDB local, lựa chọn embedding open-source hỗ trợ đa ngôn ngữ, hybrid BM25+vector, filter metadata theo part/skill, reranker.
   - `thiet-ke-sinh-cau-tra-loi` — pipeline trả lời có trích dẫn nguồn, CLI/API surface, cấu trúc repo, lộ trình triển khai theo giai đoạn, kế hoạch đánh giá (hit-rate, faithfulness).
3. **tong-hop-thiet-ke** — tổng hợp 5 phần + ràng buộc thành một tài liệu nhất quán, **tự giải quyết mâu thuẫn giữa các phần**, ghi file `docs/thiet-ke-rag-toeic.md`.
4. **tham-dinh-thiet-ke** — reviewer độc lập (read-only, hỏi "cái gì sẽ gãy / còn thiếu gì", đặc biệt: dedup có cụ thể và chạy được local trên Windows không) → `Review {approved, findings[]}`. Vòng sửa tối đa 2 round, tái dùng cùng synthesizer + reviewer (giữ ngữ cảnh, có cache).
5. **doc-thu-lan-cuoi** — cold-read lần cuối bởi agent chưa từng thấy các vòng trước: gì chưa rõ, gì tài liệu không chứng minh được → sửa một lần nếu còn vấn đề nặng, rồi xuất bản.

## Các phase (tên hiển thị cho user, tiếng Việt)
1. `Phân tích đặc thù tài liệu TOEIC` → 2. `Thiết kế song song các phân hệ` → 3. `Tổng hợp thành tài liệu thiết kế` → 4. `Thẩm định và hoàn thiện thiết kế` (vòng lặp có chặn ≤2) → 5. `Đọc thử lần cuối và xuất bản` (cold-read + `artifact.file` có try/catch tự sửa).

## Chi tiết vận hành
- Không cần `world.run` gate — deliverable là văn bản thiết kế, kiểm chứng bằng review độc lập + cold read (đúng chuẩn §3/§10 của dynamic-workflows).
- `report()` từng section khi xong và từng finding khi review, để tiến độ sống sót kể cả run gãy giữa chừng. Không dashboard (chạy ngắn, phase graph đã đủ).
- Agent names dùng ASCII (ổn định cho cache khi amend); phase/log/artifact dùng tiếng Việt có dấu.
- Sau khi xuất bản: trả `WorkflowReport` — `verified` nêu rõ tài liệu đã qua 2 lớp review độc lập; `notCovered` ghi rõ thiết kế chưa được kiểm chứng với file TOEIC thật và chưa có code.
